# EveryOps

Describe your business, and EveryOps builds the systems it needs (bookings, POS, HR, finance, content) inside one workspace. Built for the Google Cloud AI Builder Cup 2026 (submission deadline 2026-10-18). README.md has the full architecture; this file is the working rules.

## Commands

```bash
pnpm env:pull     # .env.local from Google Secret Manager (gcloud, project everyops-prod); never print or commit it
pnpm db:proxy     # Cloud SQL Auth Proxy on 127.0.0.1:5433; required for local dev, migrate and seed
pnpm db:migrate   # Better Auth tables; idempotent
pnpm db:seed      # demo account james@everyops.app / everyops2026; idempotent
pnpm dev
pnpm typecheck && pnpm lint && pnpm test && pnpm build   # all must pass before committing
```

Use pnpm only. `pnpm build` matters: `cacheComponents` errors (below) only show up there.

## Architecture boundaries

- A business's system is a **blueprint** (JSON) rendered by one generic engine (`src/lib/engine`) and one set of views. Never generate or run per-client code; AI output must be a validated blueprint or change plan (`src/lib/blueprint/validate.ts`).
- `src/lib/assistant` (interview, change planner) is where Gemini plugs in. Keep its input/output shapes so the UI doesn't change.
- Nothing is stored in localStorage. Workspaces live in Postgres: the `workspace` row holds its settings (`doc`: name, summary, current version, setup), and records, blueprint versions, history and page text have a table each (`workspace_record`, `workspace_version`, `workspace_change`, `workspace_page`; read and written only through `src/server/workspace-data.ts`), plus `workspace_member`/`workspace_invite`. `/api/workspaces` lists summaries (settings, current blueprint, counts); a workspace's records load when it opens (`ensureLoaded`). The browser saves patches, not documents (`src/lib/store/workspace-sync.ts`): only the records, versions, page text, history entries, settings or team that changed, via `PATCH /api/workspaces/[id]`. Access rules are enforced in `src/server/workspaces.ts`, never only in the UI.
- Canvas pages (`type: "canvas"`, `entityId: ""`) store `{ version: 1, shapes }` JSON in `docs` by view id; always read it through `parseCanvas`. Konva and MDXEditor need the DOM: load them with `next/dynamic` and `ssr: false`, never import them from server code.
- Layout pages (`type: "layout"`, `entityId: ""`) are built from the component library: `src/lib/components/registry.ts` holds each component's settings schema, what it points at (record types, fields of the right kind, filters, tabs, dashboard cards) and its words for the AI; `src/components/layout-page` renders it (shadcn components, shadcn charts on Recharts, blocks adapted from shadcn's dashboard blocks, and the workspace's own views and cards). The AI only arranges registered components and fills in their settings; never generate component code. To add a component: a registry entry, a renderer in `RENDERERS`, and a test. Numbers reuse the dashboard engine (`chartData`, `widgetValue`, `compareStat`) so a layout never disagrees with a dashboard card. The assistant writes a new layout as JSON in a free page's `starter` and rewrites one through `pageTexts` (turned into `replace_view`, so it's undoable), which keeps the answer schema the same size; `parseLayout` reads what Gemini wrote and `validateBlueprint` checks every reference.
- Setup ends with `withOverviewLayout` (`src/server/ai/overview-layout*.ts`): one small Gemini call arranges a layout page for the new workspace's Overview (settings come back as JSON text, so its schema stays small); parts that don't validate are dropped, and with fewer than three left (or on any failure) no layout is added. It never fails setup. It runs after `templateOverview`, and the layout is the Overview (`placeOverview`): the template cards it places stay on it as `widget` parts, the rest leave the page but stay in the workspace, where Edit layout offers them. When the Gemini step fails or keeps fewer than three parts, `withTemplateLayout` lays the template cards out as the Overview instead (numbers row, then wide and narrow cards side by side), so every workspace opens on a full, editable layout. A page with tabs and dashboard cards that no layout tab places shows those cards in a Dashboard tab, last and only when picked (`SystemPage`); the page opens on its first tab.
- Managers edit a layout page in place (Edit layout, `src/components/layout-page/layout-editor.tsx`): move parts earlier or later, make them wider or narrower, remove them, add parts from `suggestParts` (`src/lib/components/suggest.ts`: built from the workspace's own records and its unplaced cards, each checked with `validateBlueprint`) or describe one for Ask EveryOps (`useAssistant.setDraft` prefills the composer), and add, rename, move or remove sections and set their columns. The draft saves as one `replace_view` change, undoable from History. There is no drag-and-drop editor; keep it that way unless asked.
- Public layout pages (`public: true`) go through `resolveLayout` (`src/lib/public/layout.ts`): visitors get only worked-out results (numbers, chart points keyed by position, the fields a list names as text, rows numbered instead of record ids). `src/lib/components/public-safety.ts` refuses avatars, view and widget parts, lists of record types about people, and fields that name or reach a person; the validator applies it to public layouts and the resolver applies it again. A form with its own custom booking page (`FormView.page`) is never embedded on a public layout: its form part becomes a button to that page, and buttons use `visitorPageOf`. Change it there, with a test that checks the page a visitor receives.
- shadcn components live in `src/components/ui`; several are customized. Add new ones with the shadcn CLI and answer no to every overwrite (never `--overwrite`).
- Document pages (`type: "document"`, `entityId: ""`) store their markdown in `docs` by view id (the `workspace_page` table), saved through `saveDoc`; staff may save records and page text, never custom HTML. Notes and form views are ordinary record views. `applyOps` copies its ops: a plan is applied once on the server to rehearse it and again in the browser, so never let an op object end up inside the blueprint.
- Starter templates (official community systems, demo workspaces) are database rows refreshed by `pnpm db:seed` from `src/lib/catalog`. An official community system whose `source_workspace_id` is set was built with Ask EveryOps as a workspace in the demo account and published from it; the seed leaves it alone, and the demo snapshot keeps that workspace through the nightly reset. Schema changes go in a new `src/server/migrations/NNNN_name.sql` applied by `pnpm db:migrate`.
- Ask EveryOps setup: `src/server/ai/interview*.ts` (conversation) and `src/server/ai/design*.ts` (blueprint + samples, tidied and validated, up to two repairs). A repair returns a patch (`designPatch`: changed or new items whole, ids to delete in `remove`) that `applyDesignPatch` merges into the rejected design; never ask for the whole design again (a 3.7 Flash rewrite took 85–110 s, a patch takes about 5). Fix mechanical rejections in code (`tidy`, `repairStructure`, `repairRules`) before they reach a repair, and keep brief checks (`asksFor`) to explicit asks: a "Cashier" field and a "Cash Register" account type each once forced a POS into a finance tracker.
  `/api/ai/design` streams JSON lines (`DesignStreamEvent`): `stage`, `sketch` (pages, record types and views read from the partial answer with `parsePartialJson`), a `ping` every 10 s, then `done` or `error`. Setup draws it in `DesignProgress`. The design rounds stop at `DESIGN_BUDGET_MS` (220 s) so an answer always arrives inside Cloud Run's 300 s request limit; a request cut off there threw away a finished design. Closing the page aborts the Gemini calls. Samples and the Overview layout run in parallel after the design passes. `design_done` logs total ms, calls, repairs and output tokens per setup.
  The interview keeps a setup checklist (`questions`: id, question, required, answer), saved in `SetupProgress.questions` and sent back every turn. `mergeQuestions` (`setup-text.ts`) keeps questions Gemini drops and answers it blanks; `interviewTurn` refuses a design while `openRequired` isn't empty (one retry naming the open questions, then `askAgainMessage`) and appends open required questions Gemini moved on from. The questions asked on a turn come back as `ask` (each with 2-3 options, recommended first) and are answered on `QuestionCard` (`src/components/setup/question-card.tsx`) one at a time, with Other, Skip and Next; Gemini's message never lists them. Answers go out as one message of question → answer lines. `askList` adds open required questions Gemini moved on from. The side rail shows the checklist with Required/Optional marks.
  Both get `setupReferences` (`src/server/ai/references.ts`): `BUILD_PRINCIPLES` (lists the owner adds to are their own record types, every workflow has a full status lifecycle, amounts are computed, outside rates stay editable, per-period work is records), the matching playbooks and the closest community systems. Playbooks (`src/lib/catalog/playbooks*.ts`) come in two kinds: `business` (a salon, a resort; up to two match) and `system` (POS, HRIS, CRM, projects; up to two match, skipped when an `unless` playbook already covers them). Add a playbook or widen its `match` when a kind of business or system gets a thin first proposal, then add the description to the table in `playbooks.test.ts` (false matches are the usual failure: "onboarding" once matched boarding houses). Every playbook's `needs` names its record types, which lists are records, and each workflow's statuses in order (the test checks for a status lifecycle). `tidy` makes public forms usable even when Gemini forgets: it fills in form add-ons (`extras`) from the line-item types, asks for a name and a phone, un-requires fields a visitor can't answer, and shows active payment methods.
- The assistant never gets every record. It gets a digest (`src/server/ai/digest.ts`: counts, number totals, option tallies, date ranges, on-screen and small record types in full), and a lookup step before it (`src/server/ai/lookup*.ts`) lets Gemini call `aggregate`, `search_records` and `get_record` (`record-tools.ts`, SQL over `workspace_record` for that workspace); their results go into the assistant's prompt. Tools can't go on the assistant call itself: its answer schema already sits at Gemini's structural limit and even two small function declarations push it over. Compare tokens with the `{"event":"gemini"}` log lines (`assistant-lookup` plus `assistant`).
- Workspace assistant: `src/server/ai/assistant*.ts` → `/api/ai/assistant` → `src/components/assistant/assistant-panel.tsx`. It returns an answer, a question, or a `ChangePlan` (`ops` plus `recordOps`) that the browser applies through `applyChange` only after the person presses Apply. Role checks happen in the route (`canManage` for design ops, `canEdit` for record ops) and again on save in `src/server/workspaces.ts`. New plan op types go in `src/lib/engine/changes.ts` with undo support, then in the assistant schema and `toDesignOps`. Keep the Gemini schema flat: renames live in their own `renames` list because Gemini would not fill a name on rename ops inside `ops`. Measure assistant changes with a batch of real requests through `/api/ai/assistant`, not a single run.
- Everything the assistant does must be undoable. Plans apply through `applyPlan`/`undoPlan` (`src/lib/store/apply-plan.ts`): design changes are new blueprint versions, and the history entry keeps records it deleted (`removedRecords`), page text it replaced (`replacedDocs`) and the team before (`teamBefore`). Undo is newest first. Anything that can't be undone (removing a member, deleting the workspace or account, passwords) stays out of plans; the assistant links to the settings page instead. Staff saves may add data-only history entries (`mergeStaffChanges`).
- `/api/ai/assistant` streams JSON lines: `{ type: "status" }` while it works (from `onStatus` in `assistantTurn`), then `{ type: "result" }`. Answers carry `sources` (record, page or tab ids resolved by `resolveSources`). Conversations are saved per person and workspace in `assistant_thread` through `/api/ai/threads`.
- Each workspace has a memory (`workspace_memory`, `src/server/workspace-memory.ts`, shapes and merging in `src/lib/assistant/memory.ts`): the owner's standing instructions and short notes (business, preference, goal), edited in Settings → Assistant (`/api/workspaces/[id]/memory`; everyone reads, owners and admins write). It's its own table so notes the server adds never race the browser's `workspace.doc` saves. When a save clears `setup`, `patchWorkspace` turns the interview's profile and answers into notes first (`notesFromSetup`), since setup is discarded then. Every assistant turn gets the memory first in its prompt, plus `fieldUsage` (where each field is used) and excerpts of document/HTML pages; `noteMemory` (`src/server/ai/memory*.ts`, small schema, skipped by `worthRemembering` for plain lookups) runs beside the assistant call for people who can edit and returns `remembered` with the result. A plan that renames a page, tab, field, option or the workspace also rewrites document and HTML pages that spell out the old name (`renameInPages`, visible text only), as undoable page-text changes on the same plan.
- Gemini rejects the assistant's answer schema past a structural budget (properties, optional fields, enum values, union branches; descriptions don't count) with a bare 400 "invalid argument". Before adding to `assistantAnswer`, probe the full schema against Gemini; prefer one generic shape (like `remove`) or a plan-level list over repeating shapes inside `ops`.
  It sits right at that budget. Merging #15 and #17 pushed it over, so every assistant request on dev failed with "Gemini is unavailable right now". It now fits again by sharing shapes and filling defaults in `assistant.ts`: stat and progress share one widget shape, as do agenda and heatmap; the widget filter is required ("" for all); new tables leave out grouping and totals; forms leave out add-ons; and steps are written as "# Step title" entries in a form's `fieldIds` (`stepsFromMarkers`). Any new field in its schema, even a list of strings, can push it over again, so probe first.
  Document, canvas and html pages share one view shape whose type is plain text (checked against `VIEW_TYPES` in `assistant.ts`) and whose `starter` holds a document's markdown or an html page's draft; an enum there, or one more view branch, put it over.
- Assistant plans repair the usual slips before validation instead of failing: an operation that fits no shape is set aside and sent back to Gemini (`setAsideBadOps`); a public form a plan touches or a custom HTML page embeds is made public, stops requiring fields visitors can't fill and asks for a guest name and phone (`openUpPublicForms`); "multistep" requests get steps (`autoSteps`). A custom HTML page asks for a working form with `<div data-everyops-embed="formViewId">`, which `embedForms` replaces with `formSnippet` (in steps when the form has them). The assistant allows 24k-character text values for drafted pages; `runawayWatcher` treats HTML/CSS punctuation and escaped line breaks as breaks and stops a short phrase repeating for 400 characters and prose that circles through a few words (under 8% distinct in 2,000 characters; markup is exempt). A form added with a new landing page is public (the site's button opens it). `move_page` may move a page the same plan adds. Removals drop emptied pages only at the end of a plan, so a plan can replace a page's only tab.
- A form step can show some of the form's blocks (`FormStep.blockIds`, e.g. payment methods on the Payment step): `withStepBlocks` puts them in the step on public pages and the in-app form, and they leave the area below the form. The assistant writes them as `"@block_id"` entries in a form's fields next to the `"# Step title"` markers (`stepsFromMarkers`/`markersOf`); its context lists each form's fields in that format so it can rewrite them.
- Server-only code lives in `src/server` (database, auth, session). Never import it from a `"use client"` file.
- Dashboards: setup's `tidy` gives every workspace with a dated main record type (its bookings, else orders or sales) the court-bookings template's Overview (`templateOverview`, `src/lib/engine/overview-template.ts`): comparison stats with sparklines, unpaid today, revenue by day, today's schedule, needs payment and busy hours on the `overview` layout, from its own fields; the designer's other Overview widgets stay below. Cartesian charts need a definite height (`h-60`): a min-height alone renders them 0 px tall inside the dashboard grid.

- Public pages: landing views (`entityId: ""`, blocks) and form views with `public: true` are served at `/s/[workspace]/[view]` from `src/lib/public/resolve.ts`. Never send a visitor anything that function doesn't produce, never expose relation choices for people-like record types, and keep statuses and prices off public forms. HTML blocks only render in the sandboxed iframe (`allow-scripts`, never `allow-same-origin`).
- Setup's website: when a design has a public booking form, `withCustomSite` (`src/lib/public/custom-site.ts`) turns the standard landing into a custom HTML page (Emil Kowalski's motion rules, palette from the name) after samples exist, and adds a custom HTML booking page (`src/lib/public/booking-page.ts`, view `book_online` beside the landing) that visitors book on; never the standard form or form block, unless the owner asks. The form gets `FormView.page`: its own address redirects to the page, `siteOf` hides it from the menu, and the Book and hero buttons open the page (`formPageOf`/`visitorPageOf`). The form still checks and saves every booking. The page draws itself from live data through the frame bridge (`EveryOps.form/slots/days/quote/upload/submit`, answered by `HtmlPageFrame` from the same public endpoints; read calls work in previews), so courts, add-ons, prices and payment methods stay current. The bridge script goes first in `<head>` so page scripts can call it on load. Its links use `/s/__everyops_site__/<view>`; `HtmlPageFrame` fills in the slug. Booking forms pick when through `FormView.bookingLayout` (`days`, `grid`, `month`; `src/components/public/booking-pickers.tsx`); whole-day bookings (`range: "dates"`) always use the stay calendar and `/days`. The booking's own date, check-in and check-out fields follow the picked range on the client and the server.
- Records carry a `rev`. Every write goes through `putRecords`/`deleteRecords` with the rev it started from, inside a transaction holding the workspace row lock (browser patches and public submissions alike). A stale rev is a 409 with the conflicting ids; the browser pulls (`/api/workspaces/[id]/records?since=`), merges field by field (`mergeRecord`: its own edits win, numbers both sides changed add up) and saves again. Never write `workspace_record` any other way, and never send whole record lists.
- Uploads go through `src/server/storage.ts` only (bucket `UPLOAD_BUCKET`, default `everyops-prod-uploads`; `everyops-run` has objectAdmin on it). Image values must pass `isImagePath`.

## Database and auth

- Postgres database `everyops` on Cloud SQL `everyops-db` (PostgreSQL 17, project `everyops-prod`, `asia-southeast1`, connection `everyops-prod:asia-southeast1:everyops-db`), login `everyops_runtime`. Secrets in Google Secret Manager: `everyops-db-password`, `everyops-database-url`, `everyops-better-auth-secret`. Check `gcloud config get project` is `everyops-prod` (account ocampojamesss@gmail.com) before any Google Cloud change.
- Cloud Run runs as `everyops-run@everyops-prod.iam.gserviceaccount.com` (Vertex AI user, Secret Manager accessor, Cloud SQL client). Never deploy as the default compute service account.
- Kysely is the only query layer (`src/server/db.ts`); add app tables to its `Database` type. No ORM. Never open the instance to public IPs; connect through the socket or the proxy.
- Better Auth (`src/server/auth.ts`) owns `user`, `session`, `account`, `verification`; change them through its config plus `pnpm db:migrate`, never by hand.
- Browser code uses `src/lib/auth/client.ts` only (`useCurrentUser`, `useAuthReady`, `signIn`, …). Keep its `AuthResult` messages: one message for unknown email and wrong password, same confirmation whether or not a reset email exists.
- Page protection has two layers, and both are required: `src/proxy.ts` (cookie presence only, private paths in `config.matcher`) and `<Suspense><RequireSession next=…>` in the page or layout (real session check). The client `RequireAuth` guard is for sign-out transitions, not security. Server functions and route handlers must check the session themselves.
- Private: `/workspaces`, `/account`, `/w/*`. Public: `/` (signed-in home; with no session cookie `proxy.ts` rewrites it to the `/welcome` landing page), sign-in/up/reset, `/community`, `/preview/*`, `/invite/*`, legal pages. Post-auth redirects go through `safeNext()`.
- Email goes out over SMTP when `SMTP_*` is set (production); otherwise reset links are logged by `sendResetPassword`. Google sign-in turns on when `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are set.
- Nothing verifies email addresses, so every password account is unverified. Google sign-in on the same address links to it (`src/server/auth-linking.ts`, `requireLocalEmailVerified: false`) and, because Google proved the address, removes that unverified password and its sessions. Keep `auth-linking.test.ts` passing when upgrading Better Auth: a changed linking default once sent every such sign-in back to /sign-in with `account_not_linked`.

## AI

- Gemini is called only from server code in `src/server/ai` (Vertex AI, model from `GEMINI_MODEL`, default `gemini-3.7-flash`, location from `GEMINI_LOCATION`, default `global`). Never call it from the browser and never add API keys; Cloud Run uses the `everyops-run` service account and local dev uses gcloud ADC.
- Every AI feature returns structured JSON through `generateJson` with a Zod schema, and its output must pass the same validation the app already uses (`validateBlueprint`, op checks) before the user sees it. Nothing is applied without the owner's approval.
- AI routes check the session and `takeAiToken`. Keep prompts in a `*-prompt.ts` module next to the feature so they can be tested directly.
- The interview's brief is legitimately 3–8k characters, so the interview runs with `maxStringChars: 12_000` and a 40 s timeout, and `/api/ai/design` accepts briefs up to 12,000 characters. The default 3000 cut healthy briefs off and showed "Gemini didn't answer in time", and the old 8,000 cap on the route rejected a construction company's brief.
- Setup's design calls (tasks starting with `design`) run on `GEMINI_DESIGN_MODEL`/`GEMINI_DESIGN_LOCATION`, which `scripts/deploy.sh` sets to gemini-3.5-flash on asia-southeast1: it writes a design about twice as fast as 3.7 Flash. The interview, Overview layout and assistant stay on `GEMINI_MODEL`. Deploy with `GEMINI_DESIGN_MODEL=` (empty) to design on 3.7 again.
- Don't lower temperature on Gemini 3 models (they loop). gemini-3.7-flash is only served from `global`; that endpoint stalls now and then (calls with no output for 60 s), which the hedged retries absorb at the cost of time. To roll back, deploy with `GEMINI_MODEL=gemini-3.5-flash GEMINI_LOCATION=asia-southeast1`. Only the designer and the assistant set `thinking: "LOW"`.
- Gemini sometimes runs away inside a value: a string or number it never closes, repeating filler until the token limit (a minute or more). `generateJson` streams every call through `runawayWatcher` and stops it within seconds so the hedged retry starts. Vertex enforces `enum` but not `const`, `maxLength` or `maximum`; optional decorative text in a big schema is where runaways start. The designer asks for `designRequest` (no hero subheading, form button, approval labels or chart target; `tidy` fills them in) with `enumLiterals`. Test designer changes with several runs of a real brief, not one.


- `cacheComponents` is on: anything reading `headers()`, `cookies()` or awaited `params` on the server must sit inside `<Suspense>`.
- Use `proxy.ts`, not `middleware.ts`. Read `node_modules/next/dist/docs/` before using an API you haven't checked.

## Conventions

- TypeScript strict, Biome (2 spaces, 110 columns): run `pnpm exec biome check --write src scripts`. `src/components/ui` is vendored shadcn on Base UI; avoid editing it.
- UI: dark, compact, Linear-like. Tokens in `src/app/globals.css`, Geist fonts, Phosphor icons, motion per the README design rules. Times are Asia/Manila, money is PHP.
- Brand assets: `public/brand/` (SVG logos), `src/app/{favicon.ico,icon.svg,apple-icon.png,opengraph-image.png}`, `src/components/brand/logo.tsx` (stacked-bar "E"). Source files are in `../UI Mockups/branding/everyops`.
- Tests: Vitest, `src/**/*.test.ts`, for engine and logic. Test behavior, not implementation.
